# Code Patterns

- **Error handling**: Wrap errors with context using `fmt.Errorf("context: %w", err)`. Never pass a variable directly as a format string to `fmt.Errorf`/`fmt.Sprintf` (e.g. `fmt.Errorf(someVar)`) - `go vet` flags this, and it's a real bug if the variable can ever contain a `%`.
- **Config loading**: YAML with struct tags for marshaling; defaults applied in `config.Load`.
- **Templates**: Go `text/template` with embedded files via `//go:embed`.
- **CLI commands**: Each command has its own `cmd/eraser/cmd_*.go` file (e.g. `cmd_send.go`, `cmd_fill.go`) using Cobra; flags declared in the `*Cmd()` constructor, business logic in a separate `run*()` function so it's testable/callable independent of Cobra. `main.go` only holds root-command wiring and helpers shared by 3+ commands (config/profile/broker-path resolution).
- **Regexes**: Compile once at package level (`var fooRe = regexp.MustCompile(...)`), never inside a function that runs per-email/per-loop-iteration. `internal/inbox/classifier.go` and `parser.go` follow this.
- **SQLite**: `internal/history/history.go` has composite indexes (including `(profile_id, broker_id, sent_at DESC)`) for the "most recent record per broker, per profile" query pattern used throughout.
- **Multi-profile scoping**: any new `history.Store` method that reads/writes per-user data should take a `profileID string` first parameter and filter by it (see [multi-profile.md](multi-profile.md)) - the two deliberate exceptions are `ClearBrokerResponses`/`GetAllBrokerResponses`, which operate on the one shared inbox across all profiles.

## Known quirks

Worth knowing before touching related code:

- `internal/web/handlers_jobs.go`'s `processSendJob` (the web UI's background sender) and `cmd/eraser/cmd_send.go`'s `send` command both need to respect `config.Options.DailySendLimit` - they used to disagree (the web UI had its own hardcoded, provider-based limit left over from the SendGrid/Resend era). Fixed, but if you add a third send path, wire it the same way.
- `internal/web/server.go`'s `Server.config` is an `atomic.Pointer[config.Config]`, not a bare pointer - concurrent handlers and the background send-job goroutine read/write it. Always read via `s.getConfig()`; to write, load the current value, copy the struct (`newCfg := *cfg`), mutate the copy, then `s.config.Store(&newCfg)` - never mutate the struct returned by `getConfig()` in place, since another goroutine may be holding that exact pointer.
- The five by-ID methods on `internal/history/history.go`'s `Store` (`GetPendingTaskByID`, `CompletePendingTask`, `MarkTaskOpened`, `UpdateBrokerResponseClassification`, `UpdateBrokerResponseBody`) all take a `profileID string` and enforce it in the query (`AND profile_id = ?`). The getter returns `(nil, nil)` for a wrong-profile ID (same as genuinely not found); the four updaters are **silent no-ops** on a wrong-profile ID - they return `nil` either way, since a well-formed `UPDATE` matching zero rows isn't an error. If you need to know whether an update actually landed, re-fetch and check, don't trust the return value.
- `internal/browser/domain.go`'s `matchesAllowedDomain(rawURL string, allowedDomains []string) (bool, string, error)` is the one place domain-allowlist logic lives - `Browser.NavigateAndFill` and `ConfirmationHandler.ValidateDomain`/its redirect-hop check in `ClickConfirmationLink` all call it. If you add a new code path that navigates to or fetches an externally-supplied URL (e.g. from a parsed email), route it through this same allowlist rather than adding a one-off check - an empty/nil allowlist is treated as "no allowlist configured" (check passes), not "reject everything".
- The web server binds to `127.0.0.1` only (`internal/web/server.go`, `NewServer`/`Start`) - keep it that way. `gorilla/csrf` has an unpatched CSRF-bypass CVE (GO-2025-3884, no fix available upstream as of this writing); loopback-only binding is the mitigation, not the CSRF middleware itself.
- `internal/web/job.go`'s `JobManager` runs its own `Cleanup` on an hourly ticker (started in `NewJobManager`) to evict completed jobs after `jobRetention` (7 days) - if you see completed-job data missing after a week, that's why, not a bug. Jobs are also scoped per profile (`Job.ProfileID`), so two profiles can have an active send job at once.
- Fork default for `Options.Template` is `gdpr`, not upstream's `generic` (see `config.Load`, the CLI `init` prompt, and the web setup wizard's `handleSetupComplete`) - this fork exists for GDPR Article 17 use. An explicit `template:` in `config.yaml` always wins; this only fills a genuinely missing field.
- CSRF forms must use `{{.CSRFField}}` (emits `name="gorilla.csrf.Token"`, matching `gorilla/csrf`'s default field name - no `csrf.FieldName(...)` override is set). `task-helper.html` used to hand-write `<input name="csrf_token" value="{{.CSRFToken}}">`, which silently 403'd every "Mark Complete"/"Skip" click on the CAPTCHA-task helper page. Fixed - don't hand-roll the hidden input again.
- `internal/web/templates/partials/*.html` **are** invokable as named sub-templates from page templates, registered under their file name: `{{template "partials/broker-list.html" .}}`. The loader (`parseTemplates`) does `pageTmpl.New(name).Parse(partial)` for each. This used to parse them anonymously, which made them unresolvable by name and forced `brokers.html` to carry a hand-duplicated copy of the broker table that had to be edited in lockstep with the partial; that duplication is gone and must not come back. **The trap:** a partial that wraps itself in `{{define "some-name"}}` overrides the file-name entry, so if the define's name differs from the file name, the file-named entry is left *empty* - and `renderPartial` on it then emits nothing at all, with no error. `partials/profile-fields.html` is exactly that case (it defines `profile-fields`, is invoked by three setup/settings pages, and must never be `renderPartial`ed). `partials/template-preview.html` defines a name *matching* its file name, so both invocation styles work on it. Only `renderPartial` a partial with no define, or one whose define matches its file name.
- Profile form fields live in one place: add the input to `partials/profile-fields.html` **and** read it in `buildProfileFromForm` (`internal/web/handlers_profile.go`). That function takes the profile being edited as `prev` and copies forward every field it doesn't itself collect - both callers assign the result over the whole stored struct, so building a fresh `config.Profile` there silently erased anything without an input on any web-side edit (`date_of_birth` still has no input and relies on this). Whether a field is "collected" is decided by its presence in `r.Form`, not by whether it's blank: a present-but-empty input means the user cleared it and must clear the stored value, while an absent one means this page doesn't edit that field. Keying off emptiness would make list fields impossible to empty from the UI.
- The four list-valued profile fields (`additional_emails`, `name_variants`, `previous_addresses`, `additional_phones`) all go through `parseListField`/`listField` in `internal/web/handlers_profile.go`; add a new one there rather than hand-rolling a fifth parse block. Its separator set is the thing to get right: a comma may only be a separator for a field whose values can't *contain* one (emails, phones), never for names or street addresses. The same split has to hold on the CLI side (`cmd_init.go`) and in the join used to render the prompt default, or a value entered in one place is shredded by the other - `cmd/eraser/cmd_init_test.go` pins that round trip. `parseListField` also caps entry count and length (`maxListEntries`, `maxListEntryLen`): each list renders as a single unwrapped line in the email body, and RFC 5321 caps a line at 998 octets before MTAs may reject or rewrap the message.
- Template `{{if ... }}` actions are parsed literally even inside HTML/CSS *comments* in `.html` template files - a stray `{{if}}` written in a code comment (e.g. explaining a guard elsewhere in the file) will be parsed as a real unclosed action and break the whole template with a confusing "unexpected EOF" error reported against a *different* template file. Don't use `{{`/`}}` inside prose comments in `.html` templates; describe the logic in plain words instead.
- **Inbox broker matching is deliberately double-gated, and both halves matter.** An incoming email is attributed to a broker only if (a) its sender domain isn't in `inbox.unmatchableDomains`, and (b) that broker appears in `history.Store.ContactedBrokerIDs()` - i.e. we actually sent it a request. Matching is otherwise a bare `From:`-domain map lookup, and `data/brokers.yaml` maps general-purpose domains: `google-search-removal` has no contact address and a website of `google.com`, and seven brokers list free-mail contact addresses. Without the gates, 22 Google notifications and the user's own test mail were recorded as broker responses in a live database - and with `auto_archive` on, a scan would have moved that mail out of the inbox. `NewMonitor` also refuses to map a broker by website when it has no contact address, since such a broker can never reply. If you add another entry point that builds an `inbox.Monitor`, call `SetContactedBrokers` on it; a nil set disables the gate. **The gate couples inbox matching to send history:** "Clear All History" (`Store.DeleteAllHistory`) empties `removal_requests`, after which the scan matches nothing and reports a quiet inbox - correct, since there are no recorded requests to reply to, but indistinguishable from a broken scan. Both entry points say so when the contacted set is empty, and the delete endpoint says so in its response; keep that if you touch either.
- **IMAP UIDs are per-mailbox.** `inbox.Email` carries `Folder` and `UIDValidity` for this reason, and `ArchiveEmails(uids, srcFolder, destFolder, wantUIDValidity)` requires the source. Use `inbox.GroupUIDsByFolder` / `UIDValidityByFolder` to build per-folder batches - the scan reads INBOX, the archive folder and (optionally) spam into one slice, and passing that flat list to an archive call moves whichever unrelated messages happen to carry those numbers. `ArchiveEmails` additionally rejects UID 0 (go-imap encodes it as `*`, the newest message) and no-ops when source and destination are the same mailbox.
- **Never let mail leave Gmail's Spam/Trash/All Mail via copy+expunge.** `\Deleted` + `EXPUNGE` there is a permanent delete, not a label removal, and Gmail's COPY only adds a label to the same underlying message - so the "copy" is destroyed too. `ArchiveEmails` checks `Support("MOVE")` up front and refuses those source mailboxes without it. Don't call `client.UidMove` directly expecting an error on unsupported servers: go-imap v1.2.1 silently falls back to copy+store+`Expunge(nil)` internally, which is why the guarded fallback in `ArchiveEmails` sits behind an explicit capability check rather than behind `UidMove`'s error.
- **Replies are recognised two ways, and the second one is fenced.** Sender-domain matching (above) misses brokers that answer through a helpdesk tenant or a parent company - on a live account that was 8 of 74 genuine replies (`anywho.zendesk.com`, `experian-marketing-services.atlassian.net`, `mylifecs.atlassian.net`, `perion.com`, `quorum.us`, ...). So `matchReply` (`internal/inbox/replymatch.go`) also treats "the subject quotes one of the request subjects we actually sent" as a match. Because subject text is chosen by the sender, that path re-runs every sender guard first: the `unmatchableDomains` denylist, an exclusion for our own address (the monitored folder is configurable and may contain sent mail, which quotes the subject perfectly), and `isBounceEmail` (NDRs quote the subject too, and `cleanup-bounces` needs them left in the inbox). The subject set comes from `history.Store.SentTemplates`, not from every template that exists, so the weak generic subject is only live for someone who actually sends the generic template.
- **Attribution order is empirical, not intuitive.** `matchReply` tries sender domain, then helpdesk tenant (leftmost label: `anywho.zendesk.com` → `anywho`, never the registrable domain, which would be `zendesk.com`), then broker subdomain, and only last the addresses quoted in the body. Body-last is deliberate and measured: real ticketing auto-acknowledgements do not quote the message they answer ("Please type your reply above this line" plus a ticket number), and the one real body that did contain a contacted address held a sibling brand's. `brokerFromQuotedAddress` therefore also requires the body to point at exactly one broker. A reply that matches but can't be attributed gets a per-sender placeholder ID (`inbox.IsUnattributed`) and `NeedsReview` - per-sender rather than one shared sentinel, because `FindBrokerResponseBySubject` and the forms list both dedupe on broker ID and every request carries an identical subject, so a single sentinel would collapse them all into one row.
- **Spam is asymmetric on purpose.** `inbox.ArchiveDecision` moves a recognised reply out of any folder except spam, where it additionally requires the reply to have been *attributed*. Attribution depends on which brokers this user wrote to, which an outsider can't know or forge; a quoted subject alone can't pull mail out of spam. Unattributed spam is still classified and recorded with `NeedsReview` - Gmail purges spam after 30 days, so "we won't move it" must never become "you'll never see it".

## Broker disposition tags and the send gate

`broker.Broker.Tags` carries a closed vocabulary of *disposition* tags recording what a broker told us: `b2b-only` (holds no consumer data at all) and `form-only` (holds consumer data but refuses email, use `opt_out_url`). See `broker.DispositionTags`.

They live in `Tags`, not `Category`, on purpose. `Category` means **sector** and is load-bearing for the `/brokers` filter, `SelectCategories` (`send --category people-search`) and the `non-broker` invariant - overwriting it to record a disposition would silently drop a retagged broker out of `send --category marketing`. Tags are also orthogonal and multi-valued, which the two facts need.

**`Broker.Sendable()` is the one gate every send path must consult.** There are four, and they must agree:

1. `cmd/eraser/cmd_send.go` - the CLI
2. `internal/web/handlers_jobs.go` `handleAPISendOne` - the per-row Send button
3. `internal/web/handlers_jobs.go` `handleAPISendAll` (via `sendable()`) - bulk send
4. `internal/web/handlers_jobs.go` `resumePendingJob` - the paused-job resume that runs automatically at startup

Paths 2 and 4 resolve a broker by ID and so never pass through `getBrokersWithStatus`, which is where the config exclusions (`excluded_brokers`, `excluded_categories`) are applied. That is how they came to enforce less than the other two. If you add a fifth send path, call `Sendable()` in it. Note `options.regions` still has this shape of bug: it is enforced only at `cmd_send.go`, not in the web UI.

The bulk-send endpoint also accepts explicit `broker_ids`. Those are **intersected with the already-filtered, already-gated candidate list** - never resolved against `s.brokerDB` directly, which would be a way around the exclusions, the filters and the gate at once. `TestSendAllSelectionCannotBypassGates` pins this.

A disposition tag is an assertion about the *company*, not about one user's results. "They told us they are B2B-only" belongs in `brokers.yaml`; "they had no record of me" is per-user and belongs in `history.db`. `internal/inbox/classifier.go` keeps these apart: `ResponseB2BOnly` is scored separately from `ResponseRejected` precisely because "no record of you" is the normal output of a working erasure campaign and must never tag a live broker as dead.

## Broker IDs are join keys into history.db

Every record of who you have already written to - the resend cooldown (`history.SendKey`), the inbox reply gate (`ContactedBrokerIDs`), the "Sent" badge (`GetAllBrokerStatuses`) - is keyed on the broker's `id` string in `data/brokers.yaml`. **Renaming or removing an ID orphans that history, and the app will write to that broker again**, since it now reads as never-contacted. `TestShippedBrokerDatabaseIDsAreStable` pins the ID set against `internal/broker/testdata/shipped-broker-ids.txt`; retiring a broker means updating that file in the same commit and saying what happens to its history rows.

Related: `broker.Save` renormalises the whole file (quoting, key order). A no-op load-and-save of the shipped database produces an ~800-line diff, so a bulk edit that round-trips through it buries the real changes. Prefer surgical edits, or land the cosmetic churn as its own separate commit.
